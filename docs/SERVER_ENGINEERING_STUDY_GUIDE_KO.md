# PostPolio 서버 학습 가이드 (A to Z)

이 문서는 현재 프로젝트의 실제 코드 구조를 기준으로 서버를 학습할 수 있게 정리한 문서입니다.  
목표는 구현 배경을 이해하고, 기능 수정/확장/디버깅까지 수행 가능한 수준의 기준점을 제공하는 것입니다.

---

## 0) 먼저 큰 그림: 이 서버는 무엇을 하는가

현재 서버는 크게 2가지 통신 방식을 동시에 사용합니다.

- HTTP REST API: 회원가입/로그인, 그룹 CRUD, 성적, 통계, 포모도로 설정 같은 요청-응답형 작업
- Socket.IO 실시간 이벤트: 그룹 채팅, 공부 시작/종료, 랭킹/상태 업데이트 같은 실시간 상호작용

핵심 기술 스택:

- 런타임/프레임워크: Node.js + Express
- 언어/타입: TypeScript
- DB/Auth: Supabase (Postgres + Auth)
- 실시간: Socket.IO
- 검증: Zod

---

## 0-1) 왜 이 스택을 선택했는가 (의사결정 관점)

- JavaScript 기반이라 빠르게 적용 가능
- 자주 쓰이는 스택이라 레퍼런스가 많음
- Supabase 연동이 간편하고 무료 구간으로 SQL 기반 서비스 운영 가능

여기에 아래 근거를 더하면, 기술 선택의 설득력이 커집니다.

- **인지 부하 최소화**
  - 프론트(React Native)와 백엔드(Node/TypeScript)가 같은 언어권이라 문맥 전환 비용이 작습니다.
  - 소규모 팀이나 개인 개발에서 학습-구현 루프가 빠릅니다.

- **타입 기반 품질 방어**
  - TypeScript를 양쪽에서 사용하면 API 계약 불일치(필드명, nullable, 타입) 버그를 초기에 줄일 수 있습니다.
  - `shared schema`/타입 재사용 전략과 궁합이 좋습니다.

- **실시간 요구사항과의 적합성**
  - 이 프로젝트는 그룹 챗, 공부 상태 동기화 같은 실시간 요소가 핵심입니다.
  - Node + Socket.IO는 이벤트 기반 상호작용을 빠르게 구현하기 좋습니다.

- **MVP 속도와 확장성의 균형**
  - Supabase로 Auth/DB를 빠르게 붙여 MVP를 검증하고,
  - 이후 SQL 인덱스, 정책, 마이그레이션으로 점진 고도화가 가능합니다.

- **운영 복잡도 대비 생산성**
  - 초기에는 managed 서비스로 인프라 부담을 줄이고, 제품 문제 해결에 집중할 수 있습니다.
  - 무료 티어로 가설 검증을 시작하기 쉬운 장점이 있습니다.

- **유지보수성과 인재 풀**
  - JS/TS + React + Node + Postgres 조합은 인력 수급이 쉬워 협업/인수인계 리스크가 낮습니다.

- **진화 경로의 명확성**
  - 단일 서버로 시작하고, 필요 시 Redis/캐시/워커 분리/관측성 강화로 단계적으로 확장할 수 있습니다.
  - 즉, "처음부터 과설계하지 않고도 성장 가능한 스택"입니다.

정리하면, 이 선택은 단순히 유행 스택이 아니라  
**현재 문제(빠른 반복, 실시간 기능, 제한된 리소스)를 가장 현실적으로 해결하는 전략적 선택**입니다.

## 1) 컴퓨터 공학적 사고 프레임

서버를 분석할 때 아래 5가지를 함께 보면 구조 파악과 문제 분해가 쉬워집니다.

1. **입력(Input)**: 어떤 데이터가 들어오는가? (body, params, headers, socket payload)
2. **검증(Validation)**: 이 입력이 유효한가? 악의적이거나 잘못된 값은 없는가?
3. **상태(State)**: 어디에 저장되는가? (DB, 메모리, 클라이언트, 토큰)
4. **전이(Transition)**: 요청 전/후 상태가 어떻게 바뀌는가?
5. **출력(Output)**: 어떤 응답/이벤트를 누구에게 보내는가?

이 5가지를 API 하나씩 적용해보면, 설계/버그 원인을 빠르게 찾을 수 있습니다.

## 2) 디렉터리 구조와 역할

`server/src` 기준:

- `index.ts`: 서버 부트스트랩(미들웨어, 라우터, 소켓, 종료 처리)
- `routes/*`: HTTP 엔드포인트 정의 (입력 검증 + 서비스 호출 + 응답)
- `services/*`: 비즈니스 규칙 계층 (권한/정책/흐름)
- `repositories/*`: DB 접근 계층 (쿼리 책임)
- `middleware/*`: 인증, 에러, 보안, 로깅, 레이트리밋
- `socket/socketHandler.ts`: 소켓 이벤트 등록/처리
- `utils/*`: 공통 유틸(응답 포맷, 로거, async 핸들러 등)
- `types/*`: 타입 계약
- `config/env.ts`: 환경변수 검증/로딩

설계 원칙:

- Route는 얇게, Service는 규칙 중심, Repository는 데이터 접근만
- 계층이 뒤섞이면 유지보수 난이도가 급상승

## 3) 서버 시작부터 요청 처리까지 (요청 라이프사이클)

`index.ts` 흐름:

1. 보안 헤더/압축/compression 적용
2. request id 생성 + 요청 로깅
3. CORS 처리
4. body size 제한
5. API rate limit
6. health route 등록
7. API route 등록 (`/api/auth`, `/api/groups` ...)
8. 404 핸들러
9. 글로벌 에러 핸들러
10. Socket.IO 서버 생성 + 소켓 인증 미들웨어 + 이벤트 핸들러 등록

핵심 포인트:

- **미들웨어 순서가 곧 정책 우선순위**입니다.
- 에러 핸들러는 항상 마지막에 있어야 모든 에러를 받아 처리합니다.

## 4) 인증 구조: Access/Refresh Token 모델

현재 프로젝트는 Supabase Auth 기반입니다.

- 로그인 시 `accessToken + refreshToken`을 발급
- Access Token 만료 시 Refresh Token으로 재발급
- HTTP는 `Authorization: Bearer <token>`
- Socket은 handshake auth에 token 전달

서버 쪽 핵심:

- `authService.verifyToken()`으로 토큰 검증
- `expressAuthMiddleware`에서 `req.user` 주입
- `socketAuthMiddleware`에서 `socket.data.userId` 주입

설계 의도:

- 인증 로직을 라우트마다 반복하지 않고 미들웨어로 공통화
- 권한 검사 기준(유저 ID)을 이후 계층에서 일관되게 사용 가능

---

## 5) Route / Service / Repository를 한 번에 이해하기

예시: 그룹 탈퇴

1. Route (`DELETE /api/groups/:id/leave`)
   - 인증 유저 ID 추출
   - groupId 추출
   - `groupService.leaveGroup(groupId, userId)` 호출
2. Service
   - 그룹 존재 확인
   - 소유자면 탈퇴 금지
   - 멤버 여부 확인
   - 멤버 제거 실행
3. Repository
   - `group_members`에서 `(group_id, user_id)` row 삭제

이 구조의 장점:

- 규칙 변경(예: owner도 나가기 허용 + 소유권 이관) 시 Service만 중심 수정 가능
- DB 변경(테이블명/인덱스 변경)은 Repository 수정으로 캡슐화 가능

## 6) 실시간 아키텍처 (Socket.IO)

`socketHandler.ts`에서 핵심 이벤트:

- `join`: 멤버 검증 후 입장 + 히스토리 전송 + 시스템 join 브로드캐스트
- `message`: 멤버/채팅활성 여부 검증 후 저장 + 룸 브로드캐스트
- `leave`/`disconnecting`: 방 퇴장 + 시스템 leave 알림
- `study:start` / `study:stop`: 공부 세션 상태 변경 + 랭킹/멤버 공부시간 업데이트
- `study:status`: 재입장 시 현재 상태를 한 번에 동기화

컴퓨터 공학 관점:

- **Consistency**: 재입장 시 `study:status`로 서버 권위 상태(authoritative state)를 재동기화
- **Scalability**: 현재 `roomIdToUsers`는 in-memory라 단일 인스턴스 기준. 멀티 인스턴스는 Redis adapter 필요
- **Fault tolerance**: 소켓 이벤트도 try/catch + 에러 이벤트로 실패 전달

---

## 7) 입력 검증 전략 (Zod + 수동 검증)

현재 프로젝트는 두 방식 혼재:

- Zod 스키마 검증
- 일부 수동 검증 (문자열 길이, 기본값 보정 등)

학습 포인트:

- 이상적인 패턴은 Route에서 "스키마 파싱 1회" 후 Service로 전달
- 수동 보정이 필요하면, 규칙이 변하지 않도록 한 계층에 모아두는 것이 중요

운영 기준:

- 새 API는 Zod 기반으로 통일
- 에러 응답 포맷도 `sendSuccess/sendError` 또는 글로벌 에러핸들러 패턴으로 정렬

---

## 8) 에러 처리 모델

현재 에러 흐름:

- 예상 가능한 비즈니스 에러: `AppError(status, message)`
- 검증 에러: `ZodError`
- 예상 못한 에러: 500 + 로깅

`errorHandler.ts` 핵심:

- `AppError`는 statusCode 유지
- `ZodError`는 필드별 오류 정보를 구조화해 반환
- 운영 환경에서는 내부 상세를 숨기고 일반 메시지 반환

실무에서 자주 놓치는 포인트:

- "에러를 던진다"와 "에러를 사용자에게 노출한다"는 다른 문제
- 로그에는 자세히, 응답에는 안전하게

## 10) 데이터 무결성: 앱 레벨 + DB 레벨의 2중 방어

예시: 닉네임 중복 처리

- 앱 레벨: 서비스에서 사전 중복 체크 및 suffix 부여
- DB 레벨: unique index로 최종 무결성 보장

왜 2중 방어인가?

- 앱 레벨만 있으면 동시 요청 레이스컨디션 가능
- DB 제약만 있으면 사용자 경험이 거칠어짐(바로 에러)
- 둘 다 있어야 정확성과 UX를 함께 잡을 수 있음

---

## 11) 성능 사고법: 어디서 느려지는가

관측 기준:

- 요청 단위: route latency (p50/p95/p99)
- DB 단위: 쿼리 수, N+1 여부
- 소켓 단위: 이벤트 폭증, 불필요 브로드캐스트

현재 코드에서 확인되는 패턴:

- 그룹 멤버 공부시간 조회에서 배치 처리 의식
- 상태 조회를 Promise.all로 병렬 처리

추가 개선 후보:

- 자주 읽는 통계 캐싱 (TTL)
- 소켓 이벤트 디바운스/스로틀
- 필요 시 Redis 도입으로 멀티 인스턴스 실시간 일관성 확보

## 13) 트랜잭션 사고

예: 회원탈퇴는 프로필 삭제 + auth 유저 삭제 2단계 작업입니다.

질문:

- 1단계 성공, 2단계 실패하면?
- 재시도 정책은?
- 보상 트랜잭션(rollback 대체)을 둘 것인가?

핵심 포인트:

- "성공 케이스 구현"보다 "부분 실패 복구 전략"을 먼저 고민하는 습관

## 14) 테스트 전략

최소 구성:

- 단위 테스트: service 규칙(권한, 분기, 예외)
- 통합 테스트: route + middleware + 실제 test DB
- 계약 테스트: 프론트가 기대하는 응답 스키마

우선순위 높은 테스트 주제:

- 인증 실패/만료/갱신
- 그룹 owner/멤버 권한 분기
- 공부 세션 재진입 동기화 (`study:status`)
- 닉네임 중복/동시 가입 경쟁

## 15) 실전 디버깅 플레이북

문제 발생 시 순서:

1. 재현 조건 고정 (어떤 경로에서 100% 재현되는지)
2. 요청/이벤트 단위로 requestId와 userId 추적
3. route -> service -> repository 순서로 실패 지점 분리
4. DB 실제 상태와 코드 가정 비교
5. 수정 후 회귀 테스트(관련 기능 전체)

소켓 문제는 특히:

- "연결됨"과 "인증됨"과 "방 입장됨"은 서로 다른 상태임
- 재연결/중복 리스너/이벤트 타임아웃을 따로 확인해야 함

## 16) 이 프로젝트에서 확인된 강점

- 라우트 충돌 문제를 경로 우선순위로 해결 (`/upcoming` vs `/:id`)
- 실시간 상태 복원 로직을 `study:status`로 통합
- refresh token 기반 세션 유지 강화
- 그룹 멤버 공부시간 API + 소켓 이벤트로 UX와 성능 균형
- 닉네임 중복 처리에 앱/DB 양쪽 방어 적용

## 17) 기술 부채 및 개선 과제

아래 항목은 다음 개선 단계에서 우선 검토할 과제입니다.

1. 에러/응답 포맷 완전 통일 (`sendSuccess` + 글로벌 에러 기반)

3. 소유권 양도 API 구현 (현재 메시지는 있으나 실구현 부재)
4. DB 제약/인덱스 문서와 코드 규칙 동기화
5. 테스트 자동화 커버리지 확장

## 19) 코드 리뷰 받을 때 체크리스트

- 입력 검증이 route에서 보장되는가
- 권한 검사가 service에서 빠지지 않았는가
- repository가 비즈니스 로직을 갖고 있지 않은가
- 에러 응답이 일관적인가
- 로그에 디버깅 가능한 맥락(requestId/userId)이 있는가
- 성능 병목(N+1, 불필요 브로드캐스트)이 없는가
- 부분 실패 시 복구 전략이 있는가

## 20) 마지막 정리

서버 개발은 "API 하나 만들기"가 본질이 아닙니다.  
본질은 **신뢰 가능한 상태 전이 시스템**을 만드는 것입니다.

- 인증이 없는 요청은 차단되어야 하고
- 유효하지 않은 입력은 일찍 거절되어야 하며
- 권한 없는 상태 변경은 절대 일어나면 안 되고
- 실패했을 때 복구 가능해야 하고
- 운영 중에는 관측/추적 가능해야 합니다.

이 원칙을 현재 코드에 대입하면, 시스템의 안정성과 확장성 관점에서 개선 우선순위를 명확히 정리할 수 있습니다.
